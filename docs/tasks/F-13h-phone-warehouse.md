# F-13h: Phone screens for warehouse staff (Flutter)

Part of `F-13-multi-warehouse.md`. The server side (F-13a to F-13f) and the web screens (F-13g) are done. This card puts the daily warehouse jobs on the phone: receive goods, count stock, look things up.

## Survey of `apps/mobile` (2026-11-09, branch `claude/phase3-sell-8261d3`)
- **The app has no warehouse concept.** `storesOf()` (`lib/sync/store_session.dart`) keeps only locations of type `store`. The device store (`ensureTenant(stores: ...)`), every screen and `sync_pull_pos` are built around one active store. A `warehouse` role user has no store, so after sign-in there is nothing for them to work in. The only trace of the role is `CatalogScope.isWarehouse` and a `canManageStock` flag, both store-level.
- `HomeShell` always builds the store tabs (Today, Stock, POS, Utang, More). Nothing role-specific besides hiding a few cards from cashiers.
- Sync: `SyncEngine` pushes the outbox in batches through `sync_push` (kinds listed in `lib/sync/sync_engine.dart`, `posKinds`), then pulls `sync_pull_pos` / `sync_pull_catalog` with cursors. Drift schema is at **version 14** (`lib/data/db.dart`). The catalog (products and variants) is tenant-wide, so a warehouse phone already gets product names and barcodes.
- The server already accepts one warehouse op through `sync_push`: `receive_warehouse_stock` (F-13b, one line per op). Receipts against a purchase order, walk-in receipts and counts are direct RPCs today, not `sync_push` kinds.
- 63 Flutter test files exist; `flutter test` is part of `pnpm check`. Emulator `Pixel_4_API_33` is the only device.

## Decisions taken (change them here before building)
1. **Receiving works offline; counting is online-only in the first version.** Receipts only ever add stock, so replaying them later is safe. A count is measured against the system quantity *at the moment each line is counted* (F-13e). Queued offline, the server would take that snapshot at sync time, after deliveries or sales may have happened, and the correction would be wrong. Doing it properly needs the device to send its own snapshot and the server to validate it. That is a separate, riskier card (H7 below), not part of v1.
2. **Warehouse-role users get their own home** (Receive, Count, Stock, More). Owners and admins keep the store home. An owner who wants to work in a warehouse on a phone uses a "Warehouse" entry in More (H4), after v1.
3. **v1 covers:** receive against a purchase order, receive without one (walk-in), count (whole warehouse or one bin), stock lookup per warehouse and bin, scan with the existing keyboard-wedge and camera scanner. **Not in v1:** put-away and picking (bins), transfers, ordering (creating POs stays on the web).
4. **Several warehouses per user:** a picker like the store picker, and the choice is remembered on the device.

## Risks to watch
- Getting `ensureTenant` right for a user with no store (today it assumes one).
- Pulls that overwrite local unsent receipts, and `sync_push` ordering between receipts and later counts.
- A cashier or admin phone must not start pulling warehouse data (the server already scopes it; the app should not even ask).
- The phone layout: large touch targets, scan-first entry, one hand.

## H1 result (2026-11-09)
Migration `20261109000700_warehouse_sync.sql`, pgTAP `041_warehouse_sync.test.sql` (94 tests). `pnpm check` green (pgTAP 4423 in 41 files). No new tables, so no isolation-matrix rows.

- **Push:** `sync_push` gains kinds `receive_po` (payload `po_id, items, notes?, delivery_ref?`) and `receive_without_po` (payload `warehouse_id, supplier_id?, items, notes?, delivery_ref?`), as thin `op_*` wrappers over the F-13d RPCs. **The outbox op id is the goods receipt id**: a replay answers `replay: true` and changes nothing; the same op id for a different order is `id_conflict`. Refusals keep their stable hints (`location_denied`, `not_allowed`, `invalid_state`, `not_on_po`, `items_required`, `not_found`, `id_conflict`). One refused op never blocks the others in a batch. The result carries `grn_id`, `grn_no`, `po_status`, `has_discrepancy`, `without_po` for the phone to show after sync.
  `sync_push` was re-created from the newest definition (20261109000200). A refused op that names `warehouse_id` is now audited against that warehouse (before, only `location_id` was read). The existing kinds, including `receive_warehouse_stock`, are unchanged and re-tested.
- **Pull:** `sync_pull_warehouse(cursors, limit)` returns `{server_time, warehouses, bins, bin_stock_levels, stock_levels, suppliers, purchase_orders}`, each as `{rows, cursor, has_more}`, keyset paged by `(updated_at, key)` with the same 5 second hold-back as `sync_pull_pos`, limit 1 to 1000 (default 500). It runs as the caller, so row-level security decides the rows: a clerk gets only their warehouses (and only their bins, stock and orders), the owner gets every warehouse, a store admin or cashier gets nothing, tenants never mix. `stock_levels` is warehouse locations only; stores keep `sync_pull_pos`. The warehouse module must be on.
  `purchase_orders` never include drafts. The first pull (no cursor) sends only `ordered` and `partly_received` orders; after that every change, so an order that becomes `received` or `cancelled` is sent once and the phone can drop it. Lines are embedded (`id, variant_id, qty_ordered, qty_received, unit_cost`). A receive bumps the order's `updated_at`, so the new quantities arrive as a delta.
- **Counts are not queued** (decision 1 of this card). `start_count`, `record_count`, `close_count` and `cancel_count` stay online RPCs.
- Mutation checks: 20 rules broken on purpose (receipt id, notes and delivery number mapping, supplier mapping, `security definer` leaks, hold-back, module check, page size, cursor, store rows in the warehouse list and stock, drafts, first-pull filter, embedded lines, cursor handling, both new push kinds, the audit location). 19 caught at first; the survivor (walk-in delivery number dropped) exposed an assertion that only checked half of what its name claimed, now fixed and caught.
- Test technique worth reusing: rows created inside a pgTAP transaction are all "now", which the hold-back excludes; the test ages them with `session_replication_role = replica` (helper `pg_temp.age`).
- Next: H2, the local database (Drift v15) that stores this on the phone.

## H2 result (2026-11-09)

Server addendum `supabase/migrations/20261109000800_grn_result_applied_at.sql`. `pnpm check` green: Flutter 399 (was 361), pgTAP 4424.

- **Tables (v15):** `warehouses`, `wh_bins`, `wh_bin_stock`, `wh_stock` (warehouse stock, apart from the stores' `stock_levels`), `suppliers`, `purchase_orders`, `po_items`, and `wh_receipts` + `wh_receipt_items` for deliveries made on the device. The v14 to v15 step only creates tables (every row and unsent op kept) and clears any stale `wh:` cursor so the new, empty tables are filled by the first pull.
- **Numbers on screen** = the server's copy + receipts made here that the server has not caught up on. A receipt shows at once (the order's remaining falls, stock rises, goods appear in the RECEIVING bin of a bins warehouse). Over-delivery is allowed and never makes "remaining" negative.
- **Settle rule** (an effect stops being counted): the server answered the op (it sends `applied_at`, its own time of the receipt; added by the addendum migration), a COMPLETE pull has gone past that time minus the 5 s hold-back, AND the pulled order and every stock row the receipt touched are at least as new as that time. Only the server's clock is used. A confirmed effect older than a day settles regardless; a receipt the server has not answered is never settled. Settled receipts stay as history (with the server's receipt number) for 30 days, by the server's clock. A finished order is forgotten only when no unsettled receipt still needs it.
- **Checks before anything is queued** (`WarehouseReceiptException` codes `unknown_order`, `order_closed`, `not_on_order`, `duplicate_line`, `qty_invalid`, `cost_invalid`, `no_lines`, `unknown_warehouse`): all-or-nothing, nothing recorded when one line is bad.
- **Queued ops:** `receive_po` (entity = the order; payload `po_id, items, notes?, delivery_ref?`) and `receive_without_po` (entity = the warehouse; payload `warehouse_id, supplier_id?, items, notes?, delivery_ref?`), exactly what H1's `sync_push` kinds take. The op id is the receipt id. Blank notes and delivery numbers are left out.
- **Hooks for H3:** `warehouseCursors()` (cursors kept under `wh:` so they cannot clash with the store pull's `stock_levels`), `applyPullWarehouse(response)`, `warehouseOpApplied(opId, appliedAt, result)`. `discardFailed` now also removes a refused receipt's record and effect; a parked (failed, not yet discarded) receipt keeps counting.
- **Because the effect is additive, the "pull must not overwrite an order with unsent receipts" risk from the plan does not arise:** a pulled order never contains an unsent receipt, so applying it and adding the pending effect on top is always right.
- **Mutation checks:** 34 rules broken on purpose (pending ignored in orders and stock, hold-back, caught-up checks for the order and for stock, unconfirmed receipts, the one-day safety net, unfinished pulls, order forgetting, cursor namespace, every validation, payload fields, RECEIVING bin, order-line replacement, archived rows, listing order, receipt number, old-receipt cleanup, other warehouses' receipts, discard cleanup, negative remaining). 33 caught first time; the survivor (the order's copy not being checked for "caught up") exposed a missing reverse-direction test, now added and caught.
- Fixed along the way: a hard-coded `14` in the earlier v13 to v14 migration test now compares with the current schema version.
- Not done here: the sync engine does not call any of this yet (H3), and there are no screens (H4 to H6). A pull of a warehouse the user no longer has access to is not cleaned up locally (the server just stops sending it); revisit with H4's warehouse picker.

## H3 result (2026-11-09)
Files: `apps/mobile/lib/sync/sync_engine.dart`, `lib/backend.dart`, `lib/sync/store_session.dart`, `lib/data/drift_warehouse.dart` (snapshot rule), tests `test/warehouse_sync_test.dart` (19) and 6 more in `test/warehouse_store_test.dart` (now 44). `pnpm check` green: Flutter 424 (was 399), pgTAP 4424.

- **Optional `WarehouseApi`** (`pullWarehouse(cursors, limit)`), like `DeviceApi`: servers and fakes without it still work. `SupabaseBackend` implements it; a tenant that switched the warehouse module off (`module_disabled`) answers `{}`, which the store treats as "nothing to apply", so the phone is not stuck in backoff.
- **Push:** `receive_po` and `receive_without_po` (`SyncEngine.warehouseKinds`) are sent in the same `sync_push` batches as the store ops, in queue order. A batch can mix kinds. `ok` is acknowledged with `warehouseOpApplied(opId, result['applied_at'], result)` (receipt number and the server's time), `rejected` parks the op with the server's hint (existing "needs attention" list), a transient `error` stops the batch and keeps every op queued.
- **Pull:** after the push, `pullWarehouse` pages with its own cursors (`wh:` keys) until complete (max 20 pages per run; a longer pull continues next run); the store settles receipts only on a complete pull. Same 120 s idle poll, backoff and no Realtime as before.
- **Who pulls what** (`syncScopeForRole`): a `warehouse` role pulls warehouse data and NOT the store data (it has no store; saves requests and keeps warehouse stock out of the store tables); every other role (owner, admin, cashier, solo owner with a null role, unknown roles) pulls store data and never asks for warehouse data. The catalog pull is for everyone (product names and barcodes).
- **Bug found by the tests and fixed:** discarding a refused op drops all sync cursors to force a re-pull, but a cursor-less warehouse pull sends only OPEN orders, so an order that finished meanwhile was never mentioned again and stayed listed as open forever. A pull without a cursor is now a **snapshot** of the open orders: when it is complete (it may span pages; ids seen so far are kept in meta `wh_po_seen`) the local orders it did not list are forgotten. An order an unsettled receipt still needs is marked `closed` (off the open list, kept for the "caught up" judgement) instead of deleted. Delta pulls never forget anything. Known trade-off: an open order changed in the last 5 s before a snapshot is held back by the server, so it disappears for one poll and returns with the next.
- **The tests use a fake server that behaves like the real one where it matters:** it applies receipts with its own clock, stamps the order and stock rows, holds back rows newer than 5 s, pages by cursor, never sends drafts or (on a first pull) finished orders, and answers replays. They check the numbers a clerk sees at every step: offline, after the push (before the server's rows arrive), and after the pull (never dipping, never doubled), including two receipts in a row, a walk-in, another clerk's receipt on the same order, a pull that fails after a successful push, a refused receipt, a transient server error, and a replay.
- **Mutation checks:** 15 rules broken on purpose (receipts not sent through sync_push, acknowledged as store ops, store pulls always made, warehouse data always pulled, only one page, cursors not sent, data not applied, page limit ignored, snapshot never forgetting / forgetting on every pull / forgetting before the last page / deleting needed orders / never clearing its memory / reacting to an empty answer, and both directions of the role rule). 13 caught first time; two survivors showed missing tests (a completed snapshot must clear its memory), now added and caught.
- **Not verified (no unit test possible):** the real `SupabaseBackend.pullWarehouse` against a live server, including the `module_disabled` mapping. H8 (emulator acceptance) covers it. The user-facing text for the new refusal hints (`location_denied`, `invalid_state`, `not_on_po`, ...) belongs to H4/H5.
